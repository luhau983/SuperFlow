# Canvas conversion for video production

Turn finalized creative content into a canvas the user can edit, connect and continue generating from. Applies to the canvas production stage of script, novel and creative skills; creative judgment is the responsibility of the corresponding skill, and this file only explains how to implement it. For tool call conventions, see the [Canvas Operations Manual](../SKILL.md); no external materials need to be accessed.

## 0. Stage-by-stage collaboration

Seedance 2.0/2.5 multi-reference production is used by default: first complete and confirm the complete script for this scope, then generate character, location and prop assets from the script; split the complete script into multiple segments, turn all shots of each segment into one video prompt, and use the assets directly as video inputs. A segment can have multiple shots and actions and corresponds to one video node; keyframes are not generated by default. Only when the user explicitly raises special requirements such as a first frame, first and last frames or composition locking are the corresponding stages added.

Before writing asset prompts you must read [Asset image guidelines](../../script/references/assetGuide.md), and before splitting segments and writing video prompts you must read [Segment production guide](../../script/references/productionGuide.md). This file handles canvas mapping and cannot replace the specific templates above with operating instructions.

| Stage | Results shown to the user | Content advanced only after confirmation |
| --- | --- | --- |
| Requirements and brief | Known requirements, still-missing audience/duration/aspect ratio/style/sound/reference purpose | Story and script; each round asks only the few questions currently necessary |
| Complete script | Scene-by-scene text for this scope, complete actions and dialogue/OS/VO, opening, development and ending; a synopsis cannot replace the text | Extract characters, locations and props from the script; do not skip the script just because the topic is familiar |
| Asset design and preparation | Script asset list, prompts by type, character facial close-ups and front/side/back three-view sheets and other actual asset results | Generate and accept media within the confirmed scope, reuse existing qualified assets; once passed, they are available for video |
| Splitting the script into segments and video prompts | Each segment's script range, internal shots, estimated duration, continuity state and one complete multi-reference prompt | A sample of one complete segment with a clear scope; do not create generation tasks for each internal shot |
| Video sample | Actual video, checked content and what needs adjusting | After the user confirms the effect, expand to the shot range they agreed to |
| Batch production and delivery | Media for the corresponding segments, actual specs, remaining issues | Editing/compositing or the next batch; without compositing capability, deliver segments and do not claim a finished film |

- At each stage, first complete reviewable results, then use the available `askUser` to ask "continue with the current plan / adjust"; when that tool is not provided, ask in text and wait for a reply. Advance only after a real answer; do not do several unconfirmed stages in the same turn, and do not turn every tool call into a question. When generation consumes compute credits, the question clearly states this generation plan and its charging nature.
- Specific stages the user has explicitly confirmed or authorized to complete continuously are carried forward directly. Confirming the brief does not mean confirming the script, confirming asset generation does not mean accepting the generated results, and allowing one sample does not mean allowing batch production of the whole film.
- `title` and `question` of `askUser` are both required; use `fields` for multiple questions, with unique lowerCamelCase field names such as `visualStyle` and `referenceUse`. Do not pass `fields` and top-level `options` at the same time. When the form fails, fix the parameters and resend; do not treat it as the user skipping. When a stage confirmation is skipped, cancelled or unanswered, keep the results and pause; do not auto-approve, and do not ask repeatedly in a loop.
- After the user adjusts content, first synchronously update the affected brief, storyboard and node prompts, then present the updated stage results. For example, when changing to "no voiceover", do not leave the old voiceover on the canvas while generating directly with a new prompt from the chat.
- Canvas production follows the actual configuration and generation capabilities inside nodes; do not switch to other generation tools to secretly substitute a different plan in order to bypass stage confirmation or gaps in node parameters.

## 1. Read the current state, then decide which nodes are needed

Use `getCanvas` to confirm the target canvas overview, passing `include: ["nodeTypes"]` as needed to query available types. Use `findCanvasNodes` to locate existing nodes; when the ID is known, use `getCanvasNodes` directly to query the necessary fields, `getCanvasEdges` to query local connections, and `getNodeTools` to query functions. Respect pagination, truncation info and cursors, and do not read full-canvas details; complete whole-canvas tasks in batches, keeping only the current batch and summary. When producing on the current canvas, keep using the current canvas; only use the corresponding tools when a new canvas or switching to an existing work is explicitly needed.

- Choose node types from `availableNodeTypes` of `getCanvas`, and choose content modification and generation functions from the `nodeTools` list returned by `getNodeTools`, then execute them through `nodeTools`. Similar names do not mean the same capability; do not treat example names as fixed type IDs.
- Locate content by script scene number, segment number or the user's existing names; internal shot numbers are kept in the segment plan and prompts. Distinguish same-name nodes by combining text, media and connections, and when continuing work, only fill in what is currently missing.
- Text, image and video are content responsibilities; it is not mandatory to create a node for every step. Existing media outputs can be connected downstream directly, without creating another node that copies the result.
- First complete one production unit of the currently confirmed stage, fill in content and verify references, then expand to the approved scope. When assets are not confirmed, do not batch-create video nodes for the whole film, and do not first create a batch of empty nodes and fill in content later.

## 2. Put content where it can be edited

| Content | Where it goes | How it is used |
| --- | --- | --- |
| Creative brief, complete script, segment and shot table | Text node | Holds editable text and planning; not connected directly to image or video generation nodes. |
| Character, location and prop design | The image generation node of the corresponding asset | Fill in according to the asset image guidelines: character facial close-up plus complete three-view sheet, locations/props laid out by their respective types and drawing style; do not treat segment actions, dialogue or camera movement as image prompts. |
| Confirmed character images, location images, prop images | Existing media outputs or media nodes | Reuse directly and connect to the multi-reference video node; existing files are loaded into nodes through the actual media import function. |
| All shots of one segment | The prompt of one video generation node | Rewrite one three-part prompt from this segment's corresponding script and shot plan, including real media definitions, sequential shots and style constraints; do not split internal shots into multiple nodes. |
| Keyframes or first/last frames for special requirements | The corresponding image generation node | Prepare only when that route has been explicitly confirmed; not a fixed intermediate step of multi-reference production. |

The operation order is: `addNode` -> record the returned `node.id` -> `getNodeTools` to query functions -> `renameNodes` (when needed, pass a `renames` array) -> `nodeTools` to fill in content. The name can also be set directly at creation; existing nodes start from modifying content. Only creating empty nodes or leaving prompts in the chat does not count as completing the canvas setup.

Current built-in nodes may provide `node:setText`, `node:setImage`, `node:setVideo`, `node:setAudio`, `node:setPrompt`, `node:getConfig`, `node:setConfig` and the corresponding generation functions; use them only when this function list actually contains them, read the parameters from that function's description, and do not apply these names to other plugins.

What a text node writes is text content that downstream nodes can read; it is not the same as triggering the language model inside the node. When the text has already been completed by the current assistant, write it directly; it does not need to be generated again. Use `fields: ["data"], dataKeys: ["textPath"]` of `getCanvasNodes` to read the text file location, then read the actual file to verify; when you need to view the current in-memory text, read it in segments with `path: ["outputs", "text", "value"]`. The default details not including the text does not mean the node is empty; also do not guess paths or modify files directly instead of using node functions.

A new node's files or model may still be initializing. When you receive an explicit "not loaded yet" error, keep the node, handle independent content first, and try again after initialization; do not delete and rebuild, and do not confuse temporarily not loaded with a model genuinely not configured.

Media import must use files that exist and are readable. Image names, descriptions and prompts to be generated cannot be treated as image files. When existing media is on the canvas, reuse it directly; if import capability is missing, state that gap clearly, and do not pass off a text path as a media output.

## 3. Connect input dependencies, not production steps

First read the real ports on both ends, then use `connectNodes` to connect outputs to compatible inputs. Port IDs and types are taken from the latest node info. Every edge should answer "what content of the upstream does the downstream use".

- Connected text is added to the prompt in full as context, so the script and segment table cannot be connected to generation nodes as decorative lines. The assistant first reads the complete script, then rewrites this segment's original text and all internal shots into the target prompt; the script remains the content source.
- Image generation is for asset preparation; video connects directly to confirmed assets and describes the whole segment with a multi-reference prompt. One style image cannot replace the little tadpole, frog or pond assets, and a character three-view sheet cannot turn into three characters side by side in the video.
- Style images are used only for confirmed color palettes, brushwork or materials; character images constrain identity and appearance, location images constrain environmental space, prop images constrain object form. Video and audio references are added only when the current task needs them and the target actually supports them; do not mechanically connect all assets.
- For every piece of media actually used, write `{{ref N}}`, the media name and its specific purpose in the prompt; do not just connect an edge or write "if a reference image is attached". For multiple characters, state separately who does what; do not make the model guess media correspondences.
- An ordinary reference image is not inherently the first frame or last frame. First/last constraints require an actual configuration that supports that mode and the correct order; you cannot claim the setup is complete just by writing "as the first frame" in the prompt.
- Connect first, then use `nodeIds: [targetId], direction: "incoming"` of `getCanvasEdges` to page through all of the target's incoming edges. Use `fields: ["data"], dataKeys: ["referenceOrder"]` of `getCanvasNodes` to read the target's ordering, use `fields: ["ports", "outputs"]` to read source nodes in batches and verify reference numbers, and finally call the target's `node:setPrompt`. Default details do not return these fields; pagination and field truncation must be filled in according to the [canvas read rules](../SKILL.md#reading-the-canvas). Text and media share numbering, so do not always write the first image as reference 1. When the numbering cannot be confirmed, do not guess and do not trigger generation; re-verify after wiring, deletion or reordering changes.
- The order of two video nodes does not require an edge. Connect them only when the next segment actually uses the previous segment's video as an input such as a reference or continuation and the target supports it; write the editing order in names, positions or notes.

Current built-in nodes collect valid incoming edges by the target input port (usually `in`). When `data.referenceOrder[portId]` exists, sort by its keys, where a key is `encodeURIComponent(JSON.stringify([source, sourceHandle]))`; unlisted items are placed after in incoming edge order, and without an ordering configuration the incoming edge order is kept. The Nth item in the list is `{{ref N}}`. These are the basis for verification, not an interface for the assistant to modify node data directly.

At the start of the prompt, use real `{{ref N}}` to define subjects, locations, props and stable features; then, following this segment's original shot numbers, write shot by shot the action and space, a single main camera movement, complete dialogue and sound, and finally write the confirmed style and necessary constraints. For the writing approach and a complete multi-shot example, see the [Production guide](../../script/references/productionGuide.md). One sentence such as "reference the little tadpole and the pond, swim toward the frog" cannot replace the whole plot and shots of the segment, and you cannot claim the model followed accurately just because markers are present.

Upstream content used for generation must be ready. You can set up dependencies and fill in downstream prompts first, but empty outputs and images not yet generated cannot be used as ready references to start downstream.

## 4. Verify current capabilities before triggering generation

Read the generation node's actual prompt, current configuration and connected media; first present this generation's targets and quantity, model, aspect ratio/resolution/video duration, complete prompt and references, and state that costs will be incurred, then ask whether to spend compute credits on generation, and call the generation function only after explicit consent. When there is no reliable price quote for the cost, say it is unknown. This also applies to single images, variants and samples; a specific batch can be confirmed once, and additions, regenerations or retries that may incur charges beyond the approved scope must be re-confirmed. Confirming the content design or letting the assistant continue does not equal approving unexplained generation calls that consume compute credits. When the user only asks to set up or modify prompts, do not generate automatically.

Model, ratio, resolution, mode, duration and sound options must match what the user has currently confirmed. When verification is needed, read the current configuration and available model capabilities through this node's `node:getConfig`; carry forward a configuration the user has confirmed that satisfies the task, and do not re-select the model for ordinary edits. When no provider is specified, by default choose a Toonflow model in the order returned by the tool that is actually available and supports the required inputs, model and specs; the default model automatically filled in by the node does not count as user-specified; when no applicable Toonflow model exists, explain and confirm an alternative provider or model. When the production model for video has not yet been determined, choose the actually provided Seedance 2.0/2.5 multi-reference capability according to the confirmed route; do not assume it supports the required media, quantity and specs just because the name is the same. Writing "9:16" in the prompt cannot make a `16:9` node portrait, and writing "6 seconds" cannot override an actual `4` seconds.

When adjustment is needed, use the actually provided `node:setConfig` to modify only the options needed this time; parameters and supported ranges follow the function description and `node:getConfig`; when switching models, provide both the provider and the model. Configuration changes do not trigger generation; after verifying the effective result, call the generation function within the confirmed scope. Only when the target genuinely has no available configuration capability, point out the specific node and the options to adjust and ask the user to handle it. Do not stuff parameters into `node:setPrompt`, modify the canvas JSON directly, or switch to media tools to bypass the conflict.

Nodes only fill in defaults for options that are unset or incompatible: images use the lowest resolution supported by the model, with ratio defaulting to `16:9`; videos use the shortest supported duration and the corresponding lowest resolution, with ratio defaulting to `9:16`, and sound is on by default subject to the model's audio capability. Existing valid settings are not overwritten by defaults, and higher specs already confirmed by the user are not proactively changed to the default minimum.

Advance according to confirmed dependencies: complete script -> character/location/prop assets -> splitting the script into segments with per-segment multi-reference prompts -> segment sample -> the remaining approved segments. The planning table records durations; formal Seedance prompts are organized by shot number by default without writing an absolute-seconds timeline. Reuse existing assets directly, do not add keyframes shot by shot, and do not repeatedly start generation on the same node.

When a request fails, first read the error and check the current parameters. Within confirmed specs you may correct clear parameter format issues; you cannot on your own lower the resolution, shorten the duration, change model/mode, remove references or change the sound to "get it to run". These changes must first be explained in terms of impact and asked of the user. When the cause of the same type of error is not found, stop, and do not keep trying different production routes.

## 5. Handle background start and completion separately

Before starting, record the node's existing output. After the generation function returns "started", the current step is only submitted; do not immediately claim new media exists, and do not call the same generation function again to wait for the result.

- Prefer the completion notification, waiting or status capabilities the tools actually provide. When there is currently no reliable status query, do not invent query functions, and do not treat the node still existing or the old output still being visible as success.
- You can first complete other text and structural work that does not depend on this result, then read the canvas to check the output. When regenerating, the old output cannot prove this run is complete; there should be a new result or clear evidence of completion, and confirm the media is readable.
- Start downstream only when the upstream result is genuinely ready and the user confirms this stage's effect; the assistant's self-assessment cannot replace user acceptance. When there is no new result and the status cannot be confirmed, mark it as pending completion, keep the structure and dependencies already set up, and do not spin with high-frequency empty queries or resubmit repeatedly.
- Current media generation is held by the node, and unloading may cancel the task. During generation, do not switch canvases, delete or rebuild generation nodes for the sake of tidying; tidying can move positions within the same canvas.
- When only the prompt was changed this turn, the existing media is still the old version; distinguish between them when reporting that modification is done and the generation status, and do not treat the old image as the modified result.
- Changing the prompt while generation is in progress does not change the already-submitted request; to make the change take part in the next generation, first confirm the current task has ended or cancel it through an actual stop capability. Stopping the conversation also does not mean stopping the node's background task.

## 6. Example: three shots forming one video segment

Assume the confirmed complete short script is "Lin Ning pushes the door open and enters, finds a letter on the table, opens the envelope and freezes", with no dialogue. The model's actual capacity can hold this continuous event; node types, IDs and ports are still taken from the current tools.

1. Extract Lin Ning, the room and the letter from the script, reusing existing qualified media; produce missing items according to the asset image guidelines, present the character reference board, a location image without people and a prop image, and wait for confirmation.
2. Treat this continuous event as "Scene 01 - Segment 01", with three internal shots: a medium tracking shot entering the room, a close-up discovering the letter, and a fixed medium close-up observing the reaction after opening the letter. All three shots stay in the same video prompt of this segment.
3. Create only one "Scene 01 - Segment 01 - Video" node, connect the three real assets, verify the reference order, and write in three parts the media definitions, the complete actions/ambient sound of the three shots and the style constraints. The script text is not connected directly to the node, and no extra three storyboard images for the door opening, the letter and the reaction are made.
4. Verify the node's actual model, mode, duration, aspect ratio and sound; present the segment plan, complete prompt, quantity and cost; after the user explicitly approves this compute credits spending plan, call generation once; present the actual segment and ask for adjustments. Other segments continue only within the approved compute credits scope, without sending a separate request for each internal shot.
5. Use `fitCanvas` to show results; use `moveNodes` for local layout, and use `arrangeCanvas` only when the user asks to arrange the whole canvas. Multiple segments are not automatically connected by edges because of time order; when not edited, deliver them explicitly as video segments.

## 7. Verify canvas delivery

When done, use `getCanvasNodes` / `getCanvasEdges` to verify the affected nodes, text or prompts, local connections and outputs, and `fitCanvas` as needed to show this scope. Check truncation hints and, when necessary, fill in content in segments along `path`. Do not turn delivery verification into rearranging the whole canvas by default; if `arrangeCanvas` was called at the user's request, it has already fitted the viewport, so no extra arranging or repeated fitting is needed. Titles or positions cannot replace content verification.

Report separately the parts where content was written, references were established, generation was submitted, new outputs exist, review and acceptance were done, and compositing was done. When only file tools are available, do not pass off directly writing canvas files as live operations; when canvas tools are missing, keep the creative results and state clearly that the target canvas needs to be opened or the corresponding capability enabled.
