# Multi-Tenant Development Rules

These rules apply to multi-tenant architecture, data source, identity, project, settings, storage, and migration development, and must be followed together with the root `AGENTS.md`. Scoped settings, project authorization, and deployment boundaries in multi-tenant mode follow these rules; the original standalone mode remains compatible. The root rules on protecting online resources, naming, the file operation entry point, routing, and testing boundaries continue to apply.

This file records development constraints. It does not mean the related features are already implemented, nor does it authorize implementing the whole plan at once. Develop according to the stage the user has currently and explicitly requested.

For the requirement background, the user's explicit requests, the design baseline, open items, and the implementation status at handover, see [multiTenantContext.md](multiTenantContext.md). Read it before starting work, and distinguish requirement consensus, technical suggestions, and what has actually been completed.

## Product and Deployment Boundaries

- Design for commercial multi-tenancy, supporting local, enterprise server, and cloud deployments. Do not equate multi-tenancy with LAN connectivity or with a single desktop device sharing its backend.
- A tenant is the data and permission boundary, a user is a login identity, and a device is an access method; one tenant can have multiple users and devices.
- The server keeps its Web capability. Platform admin permissions are separate from tenant business permissions; local Web, desktop, mobile, and remote browsers all follow tenant authorization uniformly.
- Keep using Bun, TypeScript, ES Modules, and Express. Relational data is accessed through a single Drizzle ORM entry point, supporting both SQLite and MySQL 8.0; do not write a separate set of business logic per deployment environment.
- A single deployment keeps one Bun process and one business app created by a single `createApp` call. The private control endpoint and the `10888` creation listener may use thin transport wrappers, but both forward to the same business app; do not duplicate a second backend, configuration, model routing, or session system for the host owner or for tenants.
- The first stage allows single-instance deployment, but the design of identity, project ownership, settings, and task state must allow later multi-instance deployment, load balancing, and independent Workers. Introduce shared sessions, queues, and event facilities according to the actual stage; do not build a cluster with no requirement in advance.

## Package Structure and Dependency Boundaries

- `packages/multiTenant` is only a grouping directory for independent packages; it is not itself a workspace package and must not contain an umbrella `package.json` or an aggregate source entry. Each capability directory under it is an independent workspace package with its own `package.json`, public exports, dependencies, and typecheck configuration:

```text
packages/
  multiTenant/
    db/          # @toonflow/multi-tenant-db: data source, ORM, models, and migrations
    auth/        # @toonflow/multi-tenant-auth: accounts, passwords, admin and creation sessions
    adminWeb/    # @toonflow/multi-tenant-admin-web: admin console frontend
    userWeb/     # @toonflow/multi-tenant-user-web: creator-side account UI
    sourceMapping/ # @toonflow/multi-tenant-source-mapping: business data source mapping domain
    models/      # @toonflow/multi-tenant-models: explicit model routing, pricing, and encrypted execution snapshots
    billing/     # @toonflow/multi-tenant-billing: user wallets, reservations, and settlement ledger
    gateway/     # @toonflow/multi-tenant-gateway: unified model dispatch and billing orchestration
```

- `db` uniformly manages data source initialization, ORM adaptation, connection lifecycle, data models, migrations, and the tenant data access boundary; it must not depend on internal modules, routes, or `u.conf` of `apps/server`. The actual data directory and host capabilities needed at startup are passed in as explicit parameters.
- `adminWeb` and `userWeb` operate multi-tenant capabilities through authorized server endpoints; they do not connect to the database directly, do not read `dataSource.json`, and do not bundle database drivers, server modules, or connection credentials.
- `auth` accesses persistence through the public exports of `db`; the database package does not depend back on the auth package or the host. Authentication business logic is not stuffed into the database scaffold, and frontend packages do not depend on these two server packages.
- `sourceMapping` is an independent business domain package responsible for reading, validating, and saving the business data source mapping, persisting through the public exports of `db`. `@toonflow/multi-tenant-source-mapping/config` only exposes fields, targets, validation, snapshot contracts, and defaults for UI reuse; it must not pull in database drivers, auth, or host modules.
- `models` centrally manages explicit model routes, cost and sale prices, platform-dedicated cloud credentials, and encrypted execution snapshots; `billing` manages SQL user wallets, top-ups, reservations, settlement, and release, reusing the pricing contract of `models` and the atomic persistence of `db`. The `./config` of both packages only provides pure contracts usable by the frontend and does not pull in server domain implementations, database drivers, or secrets.
- `gateway` is an independent model orchestration domain package, not a parent umbrella package of `packages/multiTenant`. It unifies logical models, source dispatch, the public catalog, quotes, dedicated cloud configuration, execution snapshots, request digests, and the reservation / completion-settlement / execution flow; it depends one-way on the lower-level `models` and `billing` domains, and the lower-level packages must not depend back on gateway or the host.
- `packages/providerWeb` is the independent shared frontend package `@toonflow/provider-web`, serving the creation Web and the super admin console through its public `formCreate`, model editing, and provider form contracts. Pure forms work via props / events and parsing capabilities injected by the host; they do not depend on the host's Axios, Pinia, settings loading, or routing, and the original large settings panel is not moved wholesale into the pre-auth or admin consoles.
- Multi-tenant domain logic and admin-console-specific UI are concentrated in their owning independent packages; other directories are added gradually according to actual business responsibilities. Do not create unrequested modules or empty scaffolds in advance.
- `apps/server` is responsible for startup injection, HTTP adaptation, and route mounting, integrating through the public exports of the corresponding independent packages, with necessary capabilities then exposed via the host `utils.ts`; `apps/web` integrates the admin console through `@toonflow/multi-tenant-admin-web`. Neither duplicates its own multi-tenant database or permission implementation.
- `apps/web/src/main.ts` is only responsible for generic startup, mounting, and error recovery; the integration of multi-tenant sessions, the login root UI, and the admin root UI is concentrated in `apps/web/src/bootstrap/multiTenant.ts`, and the original creation App initialization lives in `apps/web/src/bootstrap/creation.ts`. Business initialization with side effects, such as business settings and MCP, must not be loaded before authentication. Later strategies such as registration continue to go into the corresponding entry point; do not accumulate business branches in `main.ts`.
- Cross-package calls use the package name and its declared public exports, do not reach into other packages' source, and no longer use the former umbrella package `@toonflow/multi-tenant` or its subpaths. The root `workspaces` must include `packages/multiTenant/*`, and new packages must register their actual dependencies and public exports accordingly.
- `packages/multiTenant` only holds source code and build configuration; runtime data source configuration, SQLite databases, and the like stay in `data/multiTenant/` under the actual data directory, and must not be written into `db`, `adminWeb`, or any package's build output directory.

## Reusing Existing Abstractions

- `apps/server/src/utils/channel` is the existing business channel entry point. Capabilities such as accounts, wallets, sub-accounts, the plugin market, the model catalog, provider sources, and the community should first reuse the `Channel` contract, `getChannel()`, and the existing HTTP adaptation; do not rebuild a parallel channel abstraction for multi-tenancy or bypass the entry point to call channel services directly. Unrequested business capabilities are not implemented in advance.
- Channels and database data sources are managed separately: `TOONFLOW_CHANNEL` selects the business channel used by the deployment, and `dataSource.json` selects the SQLite / MySQL persistence data source. The host channel integrates the corresponding capabilities of `packages/multiTenant` through public exports; the packages do not depend back on the host channel source.
- For multi-tenant integration, resolve identity and channel credentials from the authenticated user and tenant at the existing request entry point, keeping request-level parameters, tokens, and cancellation signals. Do not treat the global `settings.toonflowAccount.token` as the identity for all tenants, and do not switch channels by modifying deployment-level environment variables per request.
- `packages/file` is the existing unified file foundation entry point. Disk operations continue to use `@toonflow/file` and `@toonflow/file/bun`, reusing their atomic writes, exclusive creation, and path queues; do not duplicate native file wrappers in `packages/multiTenant` or add a new file foundation package with the same responsibility.
- Tenant authorization, project path mapping, object storage adaptation, and cross-instance business coordination belong in their owning business modules, extending existing entry points as needed. Do not mix tenant identity, ORM, business transactions, or distributed locks into the file primitives, and do not assume tenant isolation and cross-process coordination are already done just because a file abstraction exists.

## Data Directory and First Enablement

- When multi-tenancy is enabled, create a `multiTenant` folder under the application's actual data directory; the default directory structure is:

```text
data/
  settings.json
  multiTenant/
    dataSource.json
    multiTenant.sqlite
```

- The `data/` above refers to the actual data directory already determined by the startup entry point, reusing `TOONFLOW_DATA_DIR` and the existing data directory resolution rules; do not depend on `process.cwd()`, and do not write into program resource directories that may be replaced by updates.
- `data/multiTenant/` stores the base data source configuration needed for multi-tenant startup and the default SQLite database. The data source configuration is fixed as `dataSource.json`, and the default database file is `multiTenant.sqlite` in the same directory.
- On first enablement, when no data source configuration exists yet, create the following default configuration; `sqlite.file` is resolved relative to the `multiTenant` directory, and after resolution it must still be inside that directory:

```json
{
  "provider": "sqlite",
  "sqlite": {
    "file": "multiTenant.sqlite"
  }
}
```

- When multi-tenancy is not enabled, a normal startup must not automatically create the multi-tenant directory or database, or migrate old data.
- Creating the configuration for the first time uses exclusive creation; an existing configuration must be read and validated, not overwritten or reset. The enabled state is committed only after the database connection, the necessary schema initialization, and the initialization data required by the corresponding stage have all succeeded.
- Initialization failure must report a clear error, keep the existing configuration, database, and already-created content, and support safely continuing; do not automatically delete databases, records, or online objects in the name of rollback.
- Disabling multi-tenancy keeps the `multiTenant` directory, configuration, and database; it does not automatically merge user data into standalone mode, nor automatically delete tenants or projects.
- The host on/off flag is `settings.multiTenantEnabled` in `settings.json`, off by default. The data source configuration and the super admin password hash are not mixed into host settings; a normal full settings save must preserve the server's current on/off value, and only the first-time configuration and authenticated super admin endpoints may change it.

## Settings Page and Super Admin Entry

- On first entering the "Multi-tenant capability" page, read the server state; when not configured, provide the super admin account, password, confirm password, an enable-multi-tenancy switch, and a save action. The enabled state can be committed only after the account and password are validated and persisted successfully; the password must not be stored or returned in plaintext.
- Once configured, the settings page keeps the multi-tenant switch and the "Enter super admin console" entry, and no longer offers first-time password setup. The user has explicitly chosen to keep the switch, overriding the earlier plan of "only acting as a jump point once configured".
- The super admin logs in with account and password, not password only; the account field is `userName`, 1–64 characters after trimming leading and trailing whitespace, with no internal whitespace or control characters. Changing the already-configured switch from the settings page uses the same account and password verification; cancellation or failure keeps the original state.
- The user's latest request overrides the earlier "separate admin window" plan: when multi-tenancy is already enabled at desktop startup, or after it is first enabled at runtime, the main window shows the super admin console directly. Host mode persists in the current process until exit; turning the switch off afterwards only stops the creation service while the main window stays on the console, and the standalone creation entry is restored only after exiting and restarting with the switch off. Reloads, re-activation, and connection-switch navigation must not unexpectedly return to the creation home page.
- The host owner's and tenants' creation Web uniformly use `10888`, reusing the same business app; the private port is used for control, adminWeb, and native integration, and provides no creation API bypass. `createApp` only assembles the app; the desktop / standalone startup entry points call the same public multi-tenant runtime to start and stop listening, without creating the app again or starting another Bun.
- When enabled, hide the entire "Third-party models" group in settings (text models, media models) and the entire "Developer options" page, and also hide the third-party model entry in the first-run onboarding; restore the entries when disabled, and do not delete existing configuration.
- The admin console lives in the independent package `packages/multiTenant/adminWeb`, using Vue Router to provide Overview and User management, and grouping business navigation into "Model services" (Provider management, Model routes, Price configuration) and "Platform settings" (System configuration, Data source mapping). Platform-dedicated cloud credentials live in Provider management, while route bindings and prices are each maintained on their own pages; routes and components remain in the admin package, continuing to reuse the existing authentication, on/off, and creation entries, and a second set of admin business logic is not duplicated in the host.
- When the Windows SDK mistakes a Ctrl refresh for a new window, only keep valid hashes for the admin root, `/multiTenant/overview`, `/multiTenant/configuration`, `/multiTenant/users`, `/multiTenant/sourceMapping`, `/multiTenant/models`, `/multiTenant/providers`, and `/multiTenant/prices`, rebuild the host URL, and keep the `host=1` handshake marker; any other target goes back to the admin root and must not fall back to the creation home page. When adding an admin page, update this allowlist accordingly.
- Overview and configuration only show truly available information such as service status, access ports, and the creation entry; configuration actions use the existing on/off endpoints. This round has explicitly authorized the normal account management scope below, which must not be blocked by the old "unauthorized user CRUD" restriction; this authorization does not include fabricated statistics, organization tenant CRUD, member role management, subscription charging, editable database connections, or other new backends.
- Reuse the existing Toonflow logo and semantic theme variables, and support narrow-screen navigation, light and dark themes, and long translated strings; the admin redesign must not change the existing authentication, main window lifecycle, the `10888` gateway, or account isolation boundaries. Admin sessions are restored via an HttpOnly Cookie and become invalid when the current process exits; reloading the main window does not require logging in again. Admin tokens are not put into URLs, host settings, or persistent browser caches, and are not passed between windows.
- The host creator client and the admin console uniformly reuse `apps/web/src/lib/appearance.ts` to apply the theme, rather than each maintaining its own theme, primary color, font size, and border radius logic. The admin console obtains the super admin identity and a UI allowlist (theme, language, primary color, font size, border radius, etc.) from the authenticated status endpoint; it must not read or return the full host settings, provider credentials, or other secrets for the sake of syncing appearance.
- The native host identity must be proven by a random secret generated for this launch. The main window preload exchanges it via `/api/multiTenant/hostSession` for a host HttpOnly Cookie; when the creation Web is opened, a normal Web window proves the same secret via `/api/multiTenant/user/host` and then accesses legacy settings and projects as super admin. Frontend initialization waits for `window.toonflowHostReady`; the secret is not exposed to the page, not written to URLs, disk, or persistent settings, and the host admin Cookie is not treated as authorization for the public creation entry.
- Natively opened creation windows keep normal Web capabilities and are not granted RPC; native identity exchange is performed only at the explicit local `10888` creation entry. A normal browser manually visiting `10888` must log in; super admin identity must not be granted automatically based on loopback, Host, self-declared markers, or a client-supplied account ID.
- A creation window logs in automatically only on its first successful native identity exchange; later reloads use the Cookie. After an explicit logout it should return to the login page and must not log in again automatically because the preload runs again. Only a non-sensitive marker in the window session records that the exchange happened; when storage is restricted, the first login is not blocked, and the secret or token is not stored instead. The main window's host identity handshake is not affected by the creation account logging out.
- Stay compatible with the first-stage legacy auth table that only set a password: idempotently add the account column through explicit configuration or the login entry, with legacy accounts using `admin` and keeping the original password and sessions; normal status reads do not implicitly modify the schema, and do not reset or delete legacy tables and records.
- The current first-time configuration only allows the controlled host local entry, rejecting interconnected devices and proxy requests already marked as remote; console login with an existing password can be used remotely. The authorization flow for first-time initialization over the public internet in the cloud is not yet implemented; the local check must not be treated as later tenant identity authentication.

## Control Endpoint, Creator Side, and Legacy Interconnect Boundaries

- After multi-tenancy is enabled, the private control endpoint only exposes the startup handshake, necessary sessions, its own multi-tenant management, and approved native capabilities; regardless of whether a host admin Cookie or a tenant Web Cookie is carried, private creation paths such as the creation catalog, generation, projects, and user creation login all return `403`, prompting access via `10888`.
- `10888` only authenticates the host / tenant by the creation Web session, rejects admin endpoints, the legacy global providers, and platform configuration paths, and must not open all private capabilities because of the super admin role. The host Cookie may be carried to this port by a browser on the same hostname, but it must not serve as creation authorization; the host must exchange a controlled proof via `user/host` for the same Web session protocol, while normal users still log in normally.
- Host creation settings only contain `stores`, `ui`, `general`, `privacy`, `helloCompleted`, `agentSystemPrompt`, and `agentNodeTools`. Saving replaces exactly this full allowlist scope, and everything outside it is preserved from the existing platform configuration; global model / cloud account, network, MCP, on/off, and similar fields must not be read or written, and the remaining platform configuration must not be mixed into the creation DTO. The original standalone-mode protocol and the normal-user SQL settings CAS are unchanged; no host CAS was added in this round.
- `utils/multiTenant/mode.ts` uniformly provides `isEnabled` and `creationPort`; the runtime, the model gateway, and the legacy interconnect guard share the same switch, without maintaining multiple diverging on/off states. Completion of the enable response, connection close, or a `500ms` fallback notifies main window promotion only once, avoiding getting stuck on the creation entry when the response is abnormal.
- When multi-tenancy starts or is enabled, stop the legacy mobileLink listener and temporary pairing connection state, keeping `enabled` and device records, without going through the pause-configuration flow that sets enabled to false. Under host-local multi-tenancy or the current process's sticky hostMode, ignore the legacy mobileConnection active state and dynamically reject remote device switching; after disabling, restarting in standalone mode can restore the original connection configuration.
- Legacy device interconnect is kept as a standalone-mode compatibility capability and must not serve as an entry for the multi-tenant creator side to bypass `10888`; rejecting restricted switches such as mode/connect/disconnect must not rewrite the connection configuration or clear device records. The above transport and port isolation does not mean organization tenants, multi-instance deployment, or native platforms have all been verified.

## Current Account Isolation Stage

- The `10888` creation entry provides SQL-persisted registration, login, and sessions; normal accounts enter the existing creation Web after registering and logging in, and the settings menu provides the current account and a logout entry. The account UI is concentrated in the independent `userWeb` package; do not build a second creation frontend.
- Self-registration on the creation Web is controlled by the SQL platform policy `registrationEnabled`, enabled by default; legacy databases or missing policy records are likewise treated as `true` for compatibility. Only an authenticated super admin can change it through the admin configuration page and the admin endpoint; it must not be saved into normal account settings, nor may the frontend decide the policy on its own.
- The anonymous creation session returns the `registrationEnabled` boolean so the login page can decide whether to show the registration entry. When disabled, the entry is hidden and server-side registration also returns `403`; existing account login and the super admin adding normal accounts in User management are not affected. Disabling registration does not delete accounts, projects, settings, or other data.
- In this stage the only identities are super admin and normal account; organization tenants, membership, project sharing, and stable `projectId` registration are not yet implemented. The current account isolation must not be described as a complete commercial multi-tenant system or as already supporting multi-instance deployment.
- The super admin continues to access legacy projects and approved creation settings via `10888`, without reading the whole platform settings, and without automatically moving, rewriting, or assigning legacy projects to new accounts. Normal account settings are stored in their own SQL records, accept only allowed user fields, and cannot read or overwrite host configuration such as global providers, network, or MCP; saving implements CAS via a `revision`-conditional update, conflicts return `409`, and an old snapshot must not be retried unconditionally.
- A normal account's workspace is confined to `multiTenant/workspaces/<userId>/` under the actual data directory, and directory listing and file operations reuse the unified authorization entry. Account identity is determined by the authenticated session; the real path, parent/child boundaries, and symbolic links must still be checked, and the legacy project root or other accounts' directories must not be opened just because they are on the same server.
- In addition to the already isolated settings, workspace files, and read-only capabilities, this round explicitly opens to normal accounts the explicit platform model catalog, text generation, media catalog / quotes / generation, their own task status / cancellation, and their own balance; newly allowed access uses exact HTTP methods and paths. Unauthorized entries such as serverAgent, MCP, global assets, global provider management, and platform balance SSE continue to return `403`; all server capabilities must not be opened just because model routing has been integrated.

## Normal Account Management

- The user has explicitly requested a real normal account list, search with pagination, creation, enable / disable, and password reset, with the entry at the admin `/multiTenant/users`. These operations may only be performed by an authenticated super admin through admin endpoints; the public creation entry and normal accounts must not obtain admin permissions, and this must not be used to change the super admin role or add role assignment features.
- The list, search, pagination, and total count come from actual SQL normal account records; do not fabricate users, counts, or business metrics. A time field of `0` in historical records means unknown; it must not be displayed as the year 1970, nor be fabricated as the current creation time during migration.
- Disabling is an explicit account login state; the account continues to appear in the admin list and is not hidden, soft-deleted, nor are its projects or settings deleted. This round has no authorization to delete any account, database record, or online object; cleanup must not be added to reset, disable, or migration.
- The database persists an `authVersion` security version; password reset, disable, and enable must all atomically advance this version so that existing sessions become invalid. Authentication checks both the account enabled state and the session version; re-enabling only allows logging in again and does not restore old sessions.
- Creation and reset continue to use the existing account and password validation and password hashing logic; passwords, hashes, and session credentials must not be stored or returned in plaintext. Account management reuses the public exports of `db` and `auth`; the HTTP layer keeps one endpoint per file, unified validation, and error responses, and the frontend must not bypass authorization to operate on the database.

## Business Data Source Mapping and Model Integration Boundaries

- The admin `/multiTenant/sourceMapping` only shows three other business drafts: provider sources, plugins, and community; it provides no model draft switch, and model configuration goes uniformly into real model routes. The SQL contract still keeps the four fields `models`, `providers`, `plugins`, and `community` for compatibility with legacy records; saving preserves the legacy `models` field, which is not used for actual model dispatch. Targets still only allow `backend` / `toonflowCloud`, with the four legacy defaults being cloud. This is not the SQLite / MySQL connection configuration, and it does not replace `dataSource.json`.
- The mapping is saved independently in the SQL table `multiTenantSourceMapping`, not mixed into the full host settings or the registration policy. Reading and saving reuse the domain package and the ORM; saving carries a `revision` and uses CAS, old-version conflicts return `409` and keep the client's changes, without unconditional retry, reset, or record deletion.
- Only an authenticated super admin may access `GET /api/multiTenant/sourceMapping/get` and `PUT /api/multiTenant/sourceMapping/save`. The public creation gateway rejects admin paths with `403`; normal accounts or self-declared identities cannot read or modify the platform mapping.
- The user later explicitly authorized explicit model routing, pricing, and balance deduction, overriding the earlier stage restriction of "store everything as drafts only, no billing for now". Model requests are resolved uniformly through `gateway` to enabled explicit routes for actual handling, and `models` keeps the lower-level model domain responsibility; the `sourceMapping` snapshot is still `applied: false`, and its three items (provider sources, plugins, and community) are still saved only as drafts; do not claim the corresponding business has been switched over.
- Do not add cloud personal account mapping, and do not reuse the global personal cloud token to call upstream for all users. Upstream cost, user sale price, and wallets are implemented separately per the authorization for this stage below; do not add online payment, plans, or other unrequested business, and do not add empty fields or fake data.

## Unified Model Gateway and Host Boundaries

- All model entries reuse the same orchestration contract of `@toonflow/multi-tenant-gateway`. Sources register `backend` / `toonflowCloud` `ModelSource`s by the route `target` and are dispatched by the gateway; model types declare capabilities using the same adapter contract, without building parallel routing or billing facades for text, image, video, and audio.
- `apps/server/src/utils/multiTenant/gateway.ts` only does composition: injecting the actual data directory, on/off reading, source / protocol adapters, dedicated cloud resolution and loading, and price display formatting. `modelAdapters.ts` is only responsible for sources, upstream protocol structures, public capabilities, pure parameter validation, and the trusted maximum usage; entries must not duplicate price calculation, wallet state transitions, source selection, or billing branches. The legacy host `multiTenant/models.ts` and `billing.ts` have been removed, and implementations with the same responsibility must not be rebuilt in other entries.
- Admin HTTP routes and `management.ts` only do identity authorization, input validation, and forwarding; admin, catalog, quote, generation, and accounting all call the gateway uniformly. Text combines reservation, execution, and completion handling through `gateway.run`, without restoring entry-level self-orchestration such as `reserveTextCharge`; a settlement failure must not enter the refund branch for execution failure.
- The authenticated identity is passed via server-side AsyncLocalStorage, captured when the Agent model configuration is created, and retained with the runtime; every SDK turn (including summaries, sub-Agents, singleAgent, and A2A) goes through the same `gateway.run`, trusted usageTracker, quote, and finalize, and must not fall back to personal credentials or miss billing because work continues in the background. singleAgent reuses the resolved `runtimeModel` and must not go through the SDK's default model fallback by alias again; protocol metadata such as Anthropic thinking is preserved. This internal unification does not open Agent routes that originally return `403` for normal accounts.
- The gateway only projects `id` / `role` from the trusted AuthIdentity, allowing it to carry authenticated extra fields such as `userName`, so that strict internal object validation does not wrongly reject real text entries; identity must not be generated, or permissions elevated, from client self-declared fields.
- The gateway uniformly creates the encrypted execution, freezing the route, version, and upstream. The request digest is computed by the gateway over the owner, route ID / revision, the normalized request, and the explicit scope, and is bound to `requestId`; callers do not concatenate their own separate hash, nor re-read the current source to re-dispatch an already submitted request.
- Completion handling goes through unified `ModelOutcome` evidence: settle only on trusted `usage`; release only when explicitly not submitted, or failed / rejected / cancelled and not delivered; `unknown`, delivered but missing usage, or settlement failure keep the reservation. The protocol adapter layer provides trusted usage and submission / delivery evidence, and the gateway decides the accounting action; do not refund based solely on HTTP status or the cancellation signal.
- Persistent media tasks remain responsible for two-phase persistence to disk, workspace authorization, and proof of output delivery hash / actual seconds, reusing the same `reserveSnapshot` / `finalize`; they no longer decide route sale price, deduction, or wallet terminal state themselves. Stay compatible with the legacy `modelRouteCipher` and legacy request hash to recover existing pending reservations, without reading the current route, current source, or new prices to resubmit old tasks.
- Tool entries for image, video, and audio uniformly use media task start / wait, without bypassing the persistent task to call generation or provider quotes directly. When a task lacks a `chargeId`, blindly releasing by `taskId` is forbidden: it must be proven to be the same reservation via the frozen execution, owner, original scope / request hash, and `recoverExisting`, keeping the original record on conflict. Exceptions the host has confirmed as not submitted are released only with in-process WeakSet evidence, not trusting provider self-reported error codes; unknown or delivered are still held per the unified rules.
- Debug and model search that independently uses DeepSeek credentials return `403` in multi-tenant mode via a dynamic direct-access guard, re-checked right before the actual request, so they must not connect directly just because standalone mode was in effect before crossing an await. DuckDuckGo / Tavily non-model search is kept; controlled tools must follow the unified capability entry, but trusted third-party tools are not an execution sandbox, and this must not be used to claim that arbitrary plugin code is isolated.
- `apps/server/src/utils/ai/provider.ts` centralizes the provider schema, configuration reading, context and output limits, reasoning levels, and protocol capabilities, shared by AI execution and host source adaptation; the `AI → multiTenantModels → AI` runtime circular dependency must not form again.
- This round is a refactor of responsibilities and dependency direction; it does not mean introducing queues, distributed execution leases, or new cross-instance coordination capabilities. Existing identity, task ownership, idempotency, and persistence boundaries are still followed, and actual verification is recorded separately per this round's results.

## Model Routing, Dedicated Cloud Credentials, and Balance Billing

- The admin `/multiTenant/providers` maintains providers and platform-dedicated cloud credentials, `/multiTenant/models` maintains model routes, and `/multiTenant/prices` maintains user sale prices and optional upstream costs. Model, provider, and accounting admin endpoints only allow an authenticated super admin, and the public creation entry returns `403`. Saving routes uses `revision` CAS; legacy route IDs must not be removed, only disabled, and historical associations and ledger entries are not deleted.
- The public alias `publicId`, the internal permanent `route.id`, and the real `upstreamModelId` must be kept separate. For example, the creation Web requests `qwen8`, which the multi-tenant backend routes to the actual `gpt6` or a Toonflow cloud source; the admin can edit the alias and rebind the upstream, but cannot change the internal identity of an existing route. Legacy records without a `publicId` fall back to the internal UUID; aliases must not be duplicated or occupy another route's internal ID.
- Saving only checks current upstream availability for enabled routes that are newly created, newly enabled, or whose actual `type/target/providerId/upstreamModelId` binding has changed. When an existing invalid binding is unchanged, it must not block disabling, renaming, or repricing individual routes; permanent ID, schema, and CAS validation are still kept, and compatibility with legacy invalid records must not be treated as allowing new invalid bindings.
- The creator-side catalog publishes only one entry per route with `providerId: "multiTenant"` and `modelId: publicId`, carrying `routeId` for migrating legacy UUID selections; the alias and UUID must not be published as two duplicate models. Shared selection logic should find the legacy `routeId` and migrate it to the current `modelId`; legacy provider / model pairs still cannot bypass the gateway. New requests are resolved by the current binding, while historical executions, prices, and task snapshots are recovered by the original route ID / version, unaffected by renaming or rebinding.
- Text, image, video, and audio selection uniformly reuse `nodeAi` / `modelCatalog`, and the settings catalog also comes from the same source. Platform selections keep a stable `routeId`, and a fresh catalog read resolves the current `publicId` right before the actual HTTP submission; legacy UUIDs and current aliases that can still be associated are supported, while an offline legacy alias that cannot be associated with an internal route explicitly requires reselection, without guessing a binding or silently selecting another model.
- The shared language / media catalog uses a `30` second TTL, checked only on read, focus, visibility, or expand, without interval polling; shared subscriptions refresh still-mounted lists and quotes. This limit applies only to the catalog and does not remove the existing status queries of in-flight media tasks. After the admin changes an alias / sale price, a selection of the same route should update its name and price with the catalog, without forcing reselection. In multi-tenant mode, late write-backs from the legacy provider balance / SSE and personal cloud installation are disabled; the user's own SQL wallet keeps using the existing account UI, without building a separate balance state.
- Cloud credentials, provider configuration, and internal execution snapshots are encrypted with AES-GCM, with no personal cloud token fallback. The public creation DTO does not return platform provider source, configuration, or credentials; private super admin provider maintenance may read and edit source / config as authorized, and the restriction on the public DTO must not be misread as forbidding this maintenance feature. The encryption master key and platform-dedicated cloud token are not returned to the frontend.
- MySQL deployments must configure a shared `TOONFLOW_MULTI_TENANT_SECRET`, whose value is the standard Base64 of a 32-byte key; all instances use the same key. SQLite may by default exclusively create the key at the actual `data/multiTenant/modelSecret.key` with permission `0600`; a missing, corrupted, or mismatched key must report a clear error, and existing encrypted data must not be reset automatically.
- Prices are passed as decimal strings with at most six decimal places and computed as BigInt integer micro-units; currencies are only `CNY` / `USD`, and cost and user sale price are separate. Text uses four `perMillionTokens` rates for input, output, cache read, and cache write; image and audio are charged per call, and video per call or per second. Unknown required usage must not be treated as zero; when the actual charge exceeds the reservation, it is capped at the reserved amount and the platform bears the difference.
- The platform super admin is not charged against an internal wallet; a normal account only reads and spends its own wallet in the corresponding currency. The admin adds balance to a single normal account in User management; the amount must be positive and idempotent via `requestId`, with no support for negative deductions, account deletion, online payment, or plans. The account page shows the user's own balance, reservations, available balance, and the latest 20 safe ledger entries, without returning platform balance, upstream cost, or internal snapshots.
- Before calling upstream, text conservatively reserves based on the context window, maximum output, and cache read / write limits; on success it settles by actual usage and refunds the difference, and on failure it releases according to the determined state. Automatic retries of the multi-tenant model SDK are disabled; an unknown upstream result must not cause duplicate execution and charging through automatic resending.
- Media tasks persist `ownerUserId`, `modelRouteCipher`, and `chargeId`. SQL and task files follow a two-phase order: first persist the submission intent, then atomically reserve, then persist the `chargeId`, and only then allow the upstream request. For per-second video, first reserve by the requested duration, then after success probe the actual duration of the trusted output and settle.
- When `interrupted` or the upstream result is unknown, keep the reservation; release only on explicit failure / cancellation with no delivery; settle per the unified outcome when trusted usage and delivery exist; when it cannot be determined, keep the reservation for later handling. Recovery only reuses the original task, execution, and price snapshots for reconciliation and must not resubmit with a different route; reusing a reservation does not mean a task execution lease has been obtained. Settlement, release, and idempotency go through SQL atomic state transitions; a cancellation request or interruption must not be treated as a completed refund.
- The super admin may explicitly release a request that is still reserved in a user's ledger; the target user and request ID must be frozen, a reason of 1–256 characters must be given, and the operator and reason are recorded. Only the reservation record is atomically transitioned; requests already settled / released are not refunded again. After a manual release, the user is no longer charged for that request and the platform bears any still-running upstream cost; this does not mean the upstream has been cancelled, and recovery must not resubmit a released request.
- Normal task DTOs only return the user's own approved fields, without returning `providerData`, platform balance, upstream source, or credentials; status, cancellation, recovery, and ledger operations all re-check ownership. The model capabilities newly opened on the normal creation entry only allow the exact `/api/ai/models`, `/api/ai/generate`, `/api/ai/media/models`, `price`, `generate`, `tasks/status`, `tasks/cancel`, and `/api/multiTenant/user/balance`, without loosening other admin or execution entries.

## Provider Maintenance and Reusing Existing Abstractions

- Provider source / config is saved to `providerCipher` in the SQL `modelRouting` configuration, with AES-GCM purpose `providers`, isolated from the `cloud` and `execution` purposes; providers, routes, prices, and platform cloud configuration share a global `revision` CAS, cross-page stale versions return `409`, and no separate per-page versions that overwrite each other are introduced.
- When saving on the provider, route, or price pages hits `409`, keep the local unsaved input and show a visible error; do not automatically reload and overwrite the draft, nor unconditionally resubmit the old snapshot. Re-reading must go through the existing explicit interaction.
- When SQL has no provider configuration yet, the original host's text and media providers are read in a read-only, compatible way; the first save must explicitly import the complete set and keep existing provider identities, not save only the newly added item and miss legacy records. Importing does not rewrite the original `settings` or provider files, does not implicitly delete records, and reads do not trigger automatic migration.
- Keep using the original `.ts` provider abstraction and the AST parsing, VM loading, and existing SDK in `apps/server/src/utils/media/provider.ts`. Text source is parsed only as a static preset for protocol, connection configuration, rules, and models, while actual text execution continues to be done by the existing SDK; media reuses `validateMediaProviderSource`, `replaceMediaProviderModels`, and the loading primitives, without building another parser, VM, or parallel execution facade.
- The host `providerAdapters.ts` is responsible for legacy reading, normalization, description, and source checks; the gateway unifies provider reading / saving and source dispatch, and HTTP or UI must not duplicate provider parsing, migration, and execution. Provider maintenance in the admin console does not equal switching the `sourceMapping.providers` draft strategy; the not-yet-integrated boundary of that source mapping remains.
- Saving a provider only rejects changing a previously valid enabled route binding into an invalid one in this save; an already invalid legacy binding must not block editing other providers. Preserving existing provider identity, configuration validation, and the global revision CAS must still be enforced; do not delete records or re-dispatch historical tasks to work around legacy faults.
- Provider forms and model editing reuse `@toonflow/provider-web`, with networking, global state, and SQL saving injected / integrated by the host, ensuring the pre-auth and admin consoles do not load the original global settings or business side effects by importing the forms. Source-specific business text and provider implementations keep their original values, and host admin actions and validation text remain multilingual.

## Data Source and ORM

- `provider` only allows `sqlite` or `mysql`. SQLite is the default data source; MySQL 8.0 is the centralized data source that must be supported, and can be deployed locally, on enterprise servers, or as a cloud-hosted database.
- SQLite uses `data/multiTenant/multiTenant.sqlite` by default; the database and the companion files generated by the driver are managed by the ORM / database driver and must not be read, written, or overwritten as normal JSON snapshots.
- MySQL's connection host, port, database name, account, credentials, and necessary TLS configuration are managed by the same data source configuration entry; do not mix connection information into user preferences or settings readable by tenants. Credentials must not be returned to normal clients or written to logs.
- Data source configuration uses the existing Zod validation; configuration file reads and writes reuse `@toonflow/file`, full overwrites use `writeAtomic`, and existing file permission conventions are followed. The database driver's internal persistence is not rewritten onto the file primitives.
- The data source and connection lifecycle are managed uniformly by `packages/multiTenant/db`; the host integrates through public exports and exposes necessary capabilities via `utils.ts`. Re-initializing connections on every request is forbidden, as is switching the global `conf`, data source configuration, or `TOONFLOW_DATA_DIR` per request.
- Business endpoints do not depend directly on `bun:sqlite`, `mysql2`, or scattered dialect SQL. Necessary dialect differences are concentrated in the data access and migration implementations; the ORM does not guarantee that SQLite and MySQL field types, constraints, and migration syntax are fully identical.
- Switching data sources must be done through an explicit configuration and migration process, including backup, data conversion, and verification; changing the connection configuration does not equal completing a data migration. On connection or migration failure, silently falling back to a new SQLite, an empty database, or standalone mode is forbidden.
- SQLite is only for single-instance deployment; its database file must not be placed on a shared network directory for concurrent access by multiple service instances. Multi-instance deployments use centralized MySQL; all instances must connect to the same business data source and use compatible schema versions.

## Data and Settings Ownership

- Users, tenants, membership, permissions, device authorization ownership, project registration, scoped settings, and task ownership and recoverable state that need cross-instance coordination are persisted by the database.
- Configuration is scoped by host / platform, tenant, and user. Shared provider credentials, network, updates, plugin installation, and server-side execution capabilities belong to the platform admin scope; tenant policies belong to the tenant; theme, language, shortcuts, and the like belong to the user. Tenant-related user preferences also carry the tenant ownership.
- `data/settings.json` continues to serve its original role for standalone mode and host startup configuration; multi-tenant business settings are no longer saved together through the global `settings.stores` or a whole host settings snapshot.
- Each read or save may only access records within the authorized scope; normal users must not be allowed to submit a whole user, tenant, or platform settings tree that overwrites other principals' data. The current project and the recently opened list are UI state, not a basis for permissions.
- Existing formats for canvases, assets, and conversations are kept compatible per the actual development stage, and are not fully rewritten just because an ORM is introduced. Large files use file storage or object storage and are not written to database BLOBs by default.
- Legacy global assets, preferences, and personal memory belong by default to the default tenant / user of their original user; public sharing must be explicitly authorized, and legacy data must not be opened to all tenants by default.

## Identity and Project Authorization

- The request identity is produced by server-side authentication and includes the user, the selected tenant, and its permissions. `tenantId`, `userId`, directories, or object IDs sent by the client are only used to select the target, and it must be verified that the current identity is authorized to access them.
- Queries, writes, joined queries, batch operations, downloads, previews, event streams, task control, and background recovery must all verify tenant ownership; do not protect only normal JSON endpoints, and do not treat hard-to-guess UUIDs as authorization.
- The ORM entry point uniformly enforces the tenant boundary; database unique constraints, foreign key constraints, and indexes must account for tenant scope to avoid conflicts between same-named records of different tenants or cross-tenant associations.
- Multi-tenant projects use a stable `projectId`, registering the owning tenant and the actual storage location; externally, `projectId` and project-relative paths are used. Absolute disk directories must not be used as identity or authorization credentials.
- Complete the multi-tenant adaptation within the existing workspace authorization and file entry points; the frontend continues to reuse `useWorkspaceFiles`, keeping directory-call compatibility for standalone mode, and components must not concatenate file endpoints themselves.
- Local project registration uses the normalized real path; project root directories of different tenants must not be the same or overlap as parent/child. Directory boundaries, symbolic links, file conflict, and workspace root protections are still kept.
- The platform admin uniformly manages plugins, provider scripts, and external MCP, and restricts the execution capabilities tenants can invoke. Before allowing tenants to run untrusted server-side code, corresponding execution isolation such as system accounts or containers must be in place; the ORM or ordinary child processes must not be treated as a sandbox.
- Device connection, pairing, and transport authorization must be associated with the user and tenant; in the current multi-tenant stage, creation goes uniformly through `10888`, and legacy interconnect only keeps standalone-mode recovery capability. Legacy device tokens must not automatically become creation sessions, cloud accounts, or platform admin credentials; future cloud device takeover still requires account claiming and re-authorization.

## Concurrency, Transactions, and Multi-Instance

- Settings and concurrently editable project snapshots use `revision` or an equivalent version identifier. Saves carry the expected version, and the database atomically completes version comparison, content update, and version increment through a conditional update; conflicts return HTTP `409` and keep the client's changes.
- Settings in the current scope may still be fully overwritten, but an old full snapshot must not be retried unconditionally. Frontend queues, in-process server queues, and atomic file writes cannot replace cross-client version checks.
- Transactions only include necessary short database operations with a uniform lock order, and do not hold a transaction while waiting for AI, network, user input, or long file processing. Deadlock retries must be bounded and only retry database operations that are safe to repeat, without re-initiating provider charges or generation tasks.
- Local files continue to reuse the existing path locks and atomic writes; locks are held only during the actual file operation and released via `finally` on exceptions. The underlying file permit is not reentrant; do not call managed file I/O again inside a `withFileAccess` callback for the same path.
- In-process Maps, Sets, file locks, page save queues, and sticky sessions are not guarantees of cluster consistency. Task scheduling, execution leases, idempotency keys, and cancellation control need shared and recoverable state.
- In multi-instance operation, persistent project files must be held by storage accessible to all instances; a Worker's local temporary directory must not be the sole data source. Object storage adaptation stays in its owning business module and is not mixed into the local primitives of `@toonflow/file`.
- A database transaction cannot atomically commit OSS / disk files at the same time; when both are involved, define the commit order, version linkage, and recoverable state explicitly, and failures must not delete online objects or records in the name of automatic cleanup.
- Sessions, tasks, MCP control, page connections, and events must carry ownership; when passing events across instances, verify ownership and the actual connection holder. After permissions or device authorization are revoked, existing connections and task control must also be invalidated or re-verified.

## Legacy Data and Migration

- On enablement, the original user takes over the default tenant, and platform admin permissions are granted separately. Known legacy projects are registered to the default tenant by default, and other tenants initially have no access; unregistered directories are explicitly imported by the admin, without automatically scanning and opening the entire disk.
- Local legacy projects are preferably registered in place, keeping canvas, asset, and conversation formats. Other devices connecting to the service does not mean their local projects have been uploaded; cloud import must explicitly select the project and target tenant and keep the source data.
- Before project transfer, storage migration, or data source switching, first block new related operations, wait for existing saves and tasks to finish, and then commit the ownership or storage change; do not hold file locks while waiting for these tasks.
- Migrations must be able to record progress, avoid duplicate imports, and switch the data source only after verification is complete. Multiple instances must not race to run schema migrations at the same time; migrations use an independent release step or a coordinated single-execution entry, and are not implicitly bound to builds, dependency installation, or normal business requests.
- Without the user's explicit confirmation for the specific operation, online `DELETE`, `TRUNCATE`, `DROP`, soft deletion, cascading deletion, and OSS object / version deletion are forbidden; the ORM's sync, reset, migration, rollback, and cleanup capabilities are likewise subject to the root rules.

## Verification and Development Stages

- The current release keeps the multi-tenant "under development" barrier in the creation Web settings; the full configuration panel code is kept but not loaded from that entry. Restore the entry only when the user explicitly asks to reopen it; do not lift it automatically on the grounds of continuing to develop other capabilities.
- Only implement the stage the user has currently and explicitly requested; writing these rules does not mean login, tenant management, database initialization, migration, or cloud infrastructure are implemented at the same time.
- Run the existing typecheck, build, and necessary manual verification according to the changes; database and configuration verification uses isolated temporary data directories and data sources, does not connect to or overwrite real user configuration, and does not add test / self-check files or entry points.
- Report SQLite and MySQL support status separately and truthfully; when only one of them has been verified, do not claim the other is usable. Passing static checks or builds cannot substitute for actual verification of tenant isolation, concurrency, and migration behavior.
