## Core Intent

Add genuine multi-tenant capability on top of the existing Toonflow: projects, business data, settings, and execution permissions of different tenants are isolated from one another, while remaining compatible with the existing standalone mode and old projects.

The product targets future commercial deployment. It can run on a personal computer, an enterprise server, or in the cloud, and must have boundaries that allow evolving toward multiple instances, load balancing, and separate task-execution processes. It is not an online feature that merely lets LAN devices share one computer's backend.

"Host" describes the server-side role and does not refer to a specific desktop computer; "tenant" is a scope of data and permissions; "user" is a login identity; "device" is an access tool. Device interconnection, database connections, and tenant ownership are distinct concepts.

## Design Baseline Adopted in This Round

The following comes from earlier code analysis and design discussion and explains where the development rules came from; these are not completed features, nor do they mean the user has confirmed all UI and implementation details. When changing these baselines, explain their relation to the existing goals; do not quietly replace them in a local implementation.

| Original question | Current design baseline |
| --- | --- |
| Once the server becomes a host, what happens to the original Web? | Keep the Web; the Web is only an entry point. Original users can belong to the default tenant, and platform admin permissions are separate from tenant creation permissions. |
| How are old projects assigned? | Known old projects go to the default tenant first, establishing a stable `projectId` and ownership via server-side project registration; local projects are preferably registered in place, and transferred or imported explicitly by an admin. |
| Is device interconnection kept? | Keep the original configuration and standalone-mode capability; the latest entry division requires the multi-tenant host and tenants to create uniformly via `10888`, and the old interconnection must not become a bypass. Future device access still requires user/tenant authorization; connecting to the host does not mean uploading projects or gaining permissions of other principals. |
| How is old data kept compatible? | Prioritize compatibility for canvas JSON, asset paths, and conversation history; global assets, personal memory, settings, and task records must also have their ownership handled, not just a field added to the project list. |
| Will folders deadlock? | Folders themselves are not the problem. Existing locks only coordinate single-process file operations; stale-snapshot overwrites from multiple clients and cross-instance task coordination need to be solved separately. |
| How are write races on user settings avoided? | Save host/platform, tenant, and user settings in separate domains, using version-conditioned updates to prevent stale snapshots from overwriting; queuing alone or switching to SQL alone cannot automatically solve lost updates. |

- SQL primarily carries identity, ownership, permissions, settings, and runtime state that needs to be shared; introducing a database does not mean converting all assets and historical projects into database content.
- Standalone mode remains compatible; multi-tenant projects gradually use `projectId` and relative paths, with the actual disk path or object storage location resolved and authorized by the server.
- Default SQLite corresponds to single-instance use, and centralized MySQL to later multi-instance deployment. Switching databases requires explicit migration, backup, and verification; you cannot just change the connection address or silently create an empty database on failure.
- Cloud multi-instance deployments must not rely on a single instance's local directory, in-memory Map, page save queue, or sticky sessions to hold unique business state. Shared storage, queue, and event capabilities are introduced as the actual stage requires; this round is not required to launch all infrastructure at once.
- Continue to reuse the existing frontend `useWorkspaceFiles` entry, the server's path boundaries, and `@toonflow/file` primitives; tenant authorization and business storage adaptation stay in the corresponding business modules.

## Current Code State and Easily Misread Points

The following are findings from this static reading; re-verify the related changes when taking over:

- Projects in `apps/web/src/stores/workspace.ts` are still identified by absolute directory. The project list is written to server settings via `settingsStorage` in `apps/web/src/stores/settings.ts`; regular account data is written to their own SQL settings record, while the super admin and standalone mode keep the original settings. Do not treat it as data that only lives in browser localStorage.
- `apps/server/src/utils/workspace/index.ts` has added a root-directory boundary for regular accounts, and the super admin can access old projects. This stage is account workspace isolation, and cannot yet replace the later complete ownership model of "user → organization tenant → project registration".
- Global assets are in `assets/` under the data directory; media tasks are under `mediaTasks/`, associated by a hash of the project directory. Project content does not live only in the project folder; moving directories arbitrarily breaks these associations.
- Regular account settings already use SQL `revision` conditional updates, and stale-snapshot save conflicts across pages return `409`; standalone-mode settings keep the original full-snapshot protocol, and multi-tenant host creation only fully replaces the permitted whitelisted scope and keeps using the in-process queue, with no new host CAS added. Do not claim that all configuration and project snapshots have cross-client CAS.
- `apps/server/src/utils/channel` already has the `Channel` contract and deployment-level channel selection, providing business capabilities such as accounts, wallets, market, models, and provider sources. It is not the persistent connection configuration for SQLite/MySQL; the existing request adapters still need adjustment to resolve credentials per user/tenant.
- `packages/file` already provides atomic commits and an in-process path queue, which should be reused later; this does not mean cross-tenant authorization, cross-process locks, or object storage transactions are implemented.
- Agents, temporary sessions, MCP page connections, etc. have in-process state. When multi-instance support comes into play, ownership, recovery, and event routing must be handled one by one; you cannot claim load-balancing support just by adding database tables.
